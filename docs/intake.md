# Первые 30 минут с записями финала

Команды выполняются из корня MGTS в окружении с зависимостями проекта. В примерах `data/mapping` и `data/inspection` обозначают пути к двум полученным записям. Для многотомной записи ROS 2 передайте каталог с metadata.yaml и всеми томами. Для однотомной подойдёт и сам файл `.mcap` или `.db3`. Для ROS 1 укажите файл `.bag`. Если выдали архив, сначала распакуйте его и сохраните исходники отдельно.

Чтобы отрепетировать приём MCAP, выполните `python -m mgts_nav.demo out/mcap-demo --storage mcap`. Оба bag используют те же сенсоры и профиль `configs/example.json`, что и демо SQLite.

| Минуты | Действие | Что должно получиться |
|---|---|---|
| 0–5 | Запустить инвентаризацию обеих записей. Сопоставить README организаторов с именами маршрутов и форматами файлов. | Назначение каждой записи, список topic/type/count, наличие PointCloud2, Imu, Odometry, TF и камерных данных. |
| 5–10 | Запустить полный инспектор и построить черновики профилей. Для повторяющихся типов выбрать сенсор по описанию установки. | Фактические frame_id, дочерний кадр одометрии, поля облака, частоты, разрывы, повторяющиеся метки и вопросы к данным. |
| 10–18 | Проверить статическую калибровку, шкалы времени, единицы измерений и покой в начале каждого маршрута. | Для каждого сенсора известна трансформация в корпус либо явно зафиксирован незакрытый вопрос. |
| 18–23 | Сохранить поле `profile` каждого черновика как отдельный JSON и заполнить подтверждённые параметры. Выбрать срез по высоте и предел интерполяции по геометрии и частотам записи. | Два рабочих профиля. Ненужные экспериментальные режимы выключены. |
| 23–30 | Запустить построение карты, затем локализацию инспекции. При большой записи в эти минуты достаточно запустить расчёт. | Первая карта и траектория либо конкретный диагностированный блокер. |

Перед построением карты `solve` проверяет оба профиля, а также наличие, тип и число сообщений выбранных топиков в каждой записи. Это быстрая проверка метаданных. Для проверки заголовков сообщений используйте `--verify-frames` ниже.

### Команды

```powershell
python -m mgts_nav inspect data/mapping --inventory
python -m mgts_nav inspect data/inspection --inventory
python -m mgts_nav inspect data/mapping
python -m mgts_nav inspect data/inspection
python -m mgts_nav.profile data/mapping --out mapping.draft.json
python -m mgts_nav.profile data/inspection --out inspection.draft.json
```

Для выбора из нескольких потоков добавьте к команде профиля `--lidar TOPIC`, `--imu TOPIC` или `--odom TOPIC` с именем из `candidates`. Черновик содержит наблюдения и вопросы. Для рабочего `--config` нужен внутренний объект `profile` с проверенными значениями. По умолчанию профиль читает первый заголовок каждого соединения. Для проверки всей записи добавьте `--verify-frames` к командам построения обоих черновиков. В разделе `observed_frames` для каждого выбранного топика будут число прочитанных сообщений и все значения `header.frame_id`, а для одометрии также `child_frame_id`. При смене кадра зависимая калибровка останется пустой. Перед запуском карты или локализации сверьте значения из `questions` с описанием установки.

```powershell
python -m mgts_nav.calibration data/mapping --base BODY_FRAME --lidar LIDAR_FRAME --imu IMU_FRAME
python -m mgts_nav.sync data/mapping --config configs/official-map.json
python -m mgts_nav.sync data/inspection --config configs/official-inspection.json
python -m mgts_nav.solve data/mapping data/inspection --config configs/official-map.json --inspection-config configs/official-inspection.json --out out/official-01
```

Вместо BODY_FRAME, LIDAR_FRAME и IMU_FRAME подставьте имена из данных. Для быстрого запуска только обхода используйте `python -m mgts_nav map data/mapping --config configs/official-map.json --out out/official-map-01`. Все каталоги результата должны быть новыми.

### Хватит ли измерений для интерполяции

`mgts_nav.sync` читает заголовки с рабочим профилем. В JSON показаны исходные и скорректированные диапазоны времени, число сканов с доступной одометрией и число промежутков между соседними сканами с доступной IMU. Для пропусков указаны причина и границы первого и последнего случая. Проверяются края записи и внутренние разрывы с тем же порогом `max_sync_gap_s`, что и в основном загрузчике. Отключённый в профиле канал имеет статус `disabled`.

Для автоматической проверки добавьте `--require-complete`. Код выхода 0 означает успешный отчёт, а в строгом режиме также полное покрытие включённых каналов. Код 3 означает неполное покрытие или отсутствие интервалов для проверки включённой IMU. Код 2 указывает на ошибку чтения, профиля или меток, включая пустой лидарный поток. Частичное покрытие допустимо для запуска с переходом на прогноз. Физическую синхронизацию часов и покрытие времён отдельных лучей нужно проверять отдельно.

На демонстрационном MCAP обход дал 200/200 сканов с одометрией и 199/199 интервалов с IMU, инспекция — 100/100 и 99/99. В тесте со сдвигом IMU на +30 с покрытие упало до 0/99, а после компенсации вернулось к 99/99. Вставка внутреннего разрыва на одну секунду оставила 88/99 при прежних крайних метках. На двух отрезках HEAP‑1 отчёт совпал с фактической выдачей гироскопа загрузчиком для всех 39 и 59 интервалов.

Отчёт sync измеряет покрытие по заголовкам. Даже при полном покрытии интервал прогноза может остаться без угла IMU. Значение −1 в первом элементе ковариации угловой скорости исключает соответствующее измерение, включая его использование на границе интегрирования. При включённом gravity_level для оценки наклона нужны одновременно гироскоп и ускорение; после пропуска нужен новый неподвижный интервал. В обычном плоском режиме отсутствие ускорения не влияет на гироскоп. При заданном stationary_s и отсутствии всех измерений скорости в начальном неподвижном окне смещение гироскопа неизвестно, поэтому поворот IMU недоступен. Полностью нулевая матрица обозначает неизвестную ковариацию и сохраняет измерение. [Спецификация sensor_msgs/Imu](https://github.com/ros2/common_interfaces/blob/rolling/sensor_msgs/msg/Imu.msg).

### Развилки при неизвестной схеме

| Что неизвестно | Что запустить сейчас | Как подключить окончательно |
|---|---|---|
| Пользовательский тип, сжатые пакеты или отсутствующий PointCloud2 | `inspect --inventory` покажет заявленные типы без декодирования. Если уже есть отдельный стандартный PointCloud2, выбрать его через `--lidar`. | Запросить у организаторов .msg/.idl, единицы, кадр и описание кодирования. Граница чтения и декодирования в `mgts_nav/bag.py`, клиенты получают `Scan`. |
| Неизвестен TF лидара | Инвентаризация и проверка облака доступны сразу. В плоской модели для карты в раме корпуса нужны измеренные положение и вращение лидара. | Извлечь `base <- lidar` через `mgts_nav/calibration.py` либо внести паспортную калибровку в профиль. При иной системе осей сверить направление на контрольном движении. |
| Нет кинематики либо IMU | После подтверждения калибровки лидара в профиле указать для отсутствующего потока `"odom": null` или `"imu": null`. Оба допускают отключение. Для LiDAR-only нужны информативные последовательные сканы. | Адаптеры в `mgts_nav/bag.py`. При отключённой IMU поле `base_from_imu_xyzw` можно опустить. Пока IMU включена, требуется её фактическая калибровка. |
| Неясны единицы и знак времени точки | Оставить `point_time` пустым или убрать ключ. Основной режим строит карту на метках облака. | У производителя уточнить начало/конец оборота, абсолютное время или смещение, единицы s/ms/us/ns. В `mgts_nav/bag.py` используется `t_point = header.stamp + header_offset_s + offset * unit`. Для точки до метки смещение отрицательное. Абсолютные и положительные отсчёты назад от конца требуют адаптера. Компенсация в `mgts_nav/deskew.py` требует одометрии за весь интервал. |
| Камера выдаёт неизвестные признаки | Запустить `solve` без флагов визуальных пар. | Уточнить формат и соответствия ID между кадрами, ректификацию, K, оптические оси и extrinsics. Контракт пары в `mgts_nav/vision.py`, интервалы `t0,t1` в секундах на шкале лидара — в `mgts_nav/visual_fusion.py`. Проверять одну пару командой `python -m mgts_nav.vision PAIR.json`. |
| Неподвижное начало или направление гравитации не подтверждено | Указать `stationary_s: 0` в JSON и оставить `gravity_level` выключенным. Интегрирование гироскопа в этом режиме сохраняет его возможное смещение. | Сверить первые секунды гироскопа и одометрии, проверить статическое ускорение и ориентацию. После подтверждения указать длительность покоя. Логика коррекции в `mgts_nav/bag.py` и `mgts_nav/leveling.py`. |
| Автопривязка отклоняет неоднозначный старт | Сохранить отдельно результат команды `map`. При документированной стартовой позе передать `--initial X Y YAW` в метрах и радианах карты. | Уточнить старт инспекции у организаторов либо проверить привязку на информативном участке. Алгоритмы в `mgts_nav/initialization.py` и `mgts_nav/multiscan.py`. |

В результате `solve` проверить карту `map/map.pgm` вместе с `map/map.yaml`, отчёт `inspection/summary.json`, статусы и времена в `inspection/trajectory.csv`, наложение маршрута в `inspection/route.png`. Для расчёта ATE требуется независимая эталонная траектория в согласованной системе координат. При закрытом эталоне зафиксируйте долю сопоставленных сканов, длительность серий прогноза и результаты проверки повторного посещения.

### Запись ROS 2 из нескольких томов

Передайте в `solve` каталог с `metadata.yaml` и всеми файлами из `relative_file_paths`. Проверка из корня проекта в PowerShell:

```powershell
python -m pytest -q tests/test_split_bags.py
```

Тест делит каждую из двух демозаписей посередине по времени, сохраняя исходные сообщения и их метки. Для SQLite и MCAP он сравнивает CSV однокомпонентной и двухтомной записи побайтово (200 поз карты, 100 поз инспекции и непрерывная траектория). Затем тест убирает второй том инспекции. Ожидается код выхода 2 с именем недостающего файла, а каталог результата должен отсутствовать.
