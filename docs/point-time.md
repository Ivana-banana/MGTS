# Время отдельных возвратов лидара

Поле point_time задаёт имя скалярного PointField, единицу и семантику времени. Во всех режимах после компенсации точки выражены в системе корпуса на метку заголовка скана. Смещение header_offset_s.lidar переводит шкалу лидара на общую шкалу времени.

| Настройка point_time | Что записано в поле | Момент на общей шкале |
|---|---|---|
| {"field":"offset","unit":"ns"} | Смещение относительно заголовка, со знаком. Также можно задать semantics равным signed | H + C + offset × 10⁻⁹ |
| {"field":"offset","unit":"ns","semantics":"backward"} | Неотрицательная длительность от момента луча до конца скана. Заголовок должен соответствовать концу скана | H + C − offset × 10⁻⁹ |
| {"field":"timestamp","unit":"s","semantics":"absolute"} | Абсолютные секунды FLOAT64 на исходных часах заголовка лидара | timestamp + C |

H — исходный header.stamp, C — поправка часов. Для абсолютного времени код сначала вычисляет разность timestamp − H. Поправка применяется один раз. В относительных режимах допустимы s, ms, us и ns. Для абсолютного времени нужны секунды двойной точности. Шаг FLOAT64 около Unix-времени 1,7 млрд секунд составляет примерно 0,24 мкс. FLOAT32 вблизи той же эпохи имеет шаг порядка 128 секунд и отклоняется. Поле на независимых часах датчика требует предварительной синхронизации. Метка доставки ROS bag для компенсации не используется.

## Проверка

Из корня MGTS в Windows PowerShell:

```powershell
& .\.venv-mgts\Scripts\python.exe -m pytest -q -s tests/test_point_time_semantics.py
```

Сценарий записывает одни и те же движущиеся лучи в три bag ROS 2. Заголовок привязан к концу оборота, его сырые часы отстают на 0,25 с, а первый исправленный скан имеет метку 1700000000,095 с. Проверены все 100 сканов без пропуска одометрии и все 100 с внутренним пропуском. При пропуске отклонены сканы 40–45 включительно (индексы от нуля), остальные обработаны. Времена, размеры облаков и причины отказов совпали. Максимальное расхождение координат со знаковым смещением составило 0 м для отсчёта назад и 0,000000319 м для абсолютной метки. Отдельный аналитический контроль проверяет координату известной стены на ускоряющейся платформе.

## Поворотная компенсация по IMU

Штатные map и localize, а также обе стадии solve принимают профиль с таким полем:

```json
"point_time": {"field": "time", "unit": "s", "motion": "gyro"}
```

Укажите реальный топик и систему координат IMU, кватернион base_from_imu_xyzw, перенос и поворот лидара. Используются исправленные часы обоих датчиков и те же соглашения signed/backward/absolute. На каждом интервале угловая скорость в системе корпуса интегрируется трапециями, затем угол интерполируется на метки точек и заголовка. При stationary_s > 0 учитывается оценка смещения гироскопа на стартовом участке. Точки сначала переводятся в систему корпуса, поэтому перенос крепления лидара входит в геометрию поворота. При gravity_level применяется существующая оценка вертикали на метке скана и скорости изменения курса. Модель компенсирует плоский поворот. Перенос корпуса и изменение крена/тангажа между отдельными возвратами остаются в измерениях.

По умолчанию без point_time коррекция выключена. При наличии point_time без motion действует прежняя кинематическая компенсация. Для gyro требуется полностью покрытый интервал от самой ранней из точек и заголовка до самой поздней метки. Экстраполяция запрещена. Если нет нужной границы, есть разрыв больше max_sync_gap_s либо недоступное измерение угловой скорости, весь скан получает причину deskew_imu_unavailable. У кинематического режима сохраняется deskew_odom_unavailable. Это отличается от исследовательского конвертера №90, который копировал непокрытые сканы как исходные XYZ.

### Полевая проверка

Исходный XYZ bag HEAP-1 не содержит времени точек. Для подготовки bag с исходным FLOAT64 time используйте проверенный архив и данные из [эксперимента №90](heap1-point-times.md). Экспорт сверяет SHA-256 архива, XYZ, количество точек, заголовок и метку записи каждого сообщения.

```powershell
$python = '.\.venv-mgts\Scripts\python.exe'
$run = 'out/gyro-cli-104'
New-Item -ItemType Directory -Force $run | Out-Null
foreach ($role in 'mapping','inspection') {
    & $python -m tools.heap1_timed_bag out/heap1-timing-90/velodyne_points.tar out/heap1-long-80 $role "$run/$role"
}
$cfg = Get-Content out/heap1-long-80/profile.json -Raw | ConvertFrom-Json
$cfg | Add-Member -NotePropertyName point_time -NotePropertyValue @{field='time'; unit='s'; motion='gyro'}
$cfg | ConvertTo-Json -Depth 8 | Set-Content -Encoding utf8 "$run/profile.json"
& $python -m mgts_nav map "$run/mapping" --config "$run/profile.json" --resolution .08 --out "$run/map"
& $python -m mgts_nav localize "$run/inspection" --config "$run/profile.json" --map out/heap1-factorial-96/both/map/map.yaml --initial 0.9579082508672263 1.254084931557723 -0.015250987212696908 --out "$run/known"
```

Координаты всех точек сверены в системе корпуса до среза по высоте и воксельной фильтрации со сканами независимой подготовки №90/102. Для 298 покрытых оборотов обхода максимальное евклидово расхождение составило 7,42 мкм, для 58 оборотов инспекции — 8,46 мкм (верхние округлённые границы). Исследовательский bag хранит исправленные XYZ в float32. У каждого окна обоим крайним оборотам не хватило покрытия. На карте №96 с известным стартом штатный localize сопоставил 58/60 сканов, на двух остальных сохранил прогноз и диагностические метки. Эта проверка измеряет воспроизводимость геометрии на одной миссии.

В штатном map по этому профилю получено 300 строк: один origin, 297 matched и два prediction_only с причиной deskew_imu_unavailable. Аналитический тест использует вертикальную стену x=4 м, лучи за 100 мс до и через 100 мс после заголовка, ненулевое плечо лидара и разные поправки часов IMU/лидара. Проверены обе непокрытые границы, разрыв, признак недоступного гироскопа и отсутствие топика IMU в профиле.
