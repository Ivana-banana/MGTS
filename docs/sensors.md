# Подключение сенсоров и проверка результата

## Калибровка и время

`python -m mgts_nav inspect BAG --inventory` читает состав топиков без декодирования датчиков. Обычный `inspect BAG` дополнительно читает сообщения с заголовками, выводит частоты, разрывы, повторения меток, кадры и поля облака. Разность между временем записи и заголовка включает транспортную задержку. Для поправки часов нужен отдельный источник синхронизации.

```sh
python -m mgts_nav.calibration BAG --base base_link --lidar lidar_frame --imu imu_frame
```

Команда собирает цепочки из сообщений `/tf_static` и выдаёт экструзику в виде параметров профиля. Указанные имена кадров — пример. Если калибровка поставлена отдельным файлом, перенесите в профиль вращение и смещение **из сенсора в базу**. Лидар и IMU могут быть установлены с разными ориентациями. Для `Odometry` исходный тип должен содержать позу именно кадра робота в его локальной системе одометрии.

| Необязательный ключ профиля | Смысл и момент включения |
|---|---|
| `"header_offset_s": {"imu": 0.012}` | Пример добавляет 12 мс к каждой исходной метке IMU. Для всех устройств по умолчанию поправка нулевая. |
| `"point_time": {"field":"offset_time","unit":"ns"}` | Время **относительно метки скана**. Момент измерения равен времени скана плюс значение поля в заданных единицах (s, ms, us или ns). Проверьте знак, тип и точку отсчёта у организаторов. Абсолютный timestamp требует преобразования в адаптере. |
| `"gravity_level": true` | Включает оценку крена и тангажа по угловой скорости и удельной силе в базе, затем выравнивает облако перед высотным срезом. Нужен валидный неподвижный старт. В покое акселерометр должен показывать около +9,81 м/с² вверх. |
| `"imu": null` или `"odom": null` | Явное отключение вспомогательного канала для абляции. Режим выравнивания требует IMU, компенсация движения — кинематическую одометрию. |

Компенсация движения использует плоские приращения каждой точки. При пропуске одометрии внутри скана этот скан не корректирует карту. При потере оценки вертикали выравнивание возобновляется после нового неподвижного отрезка. Длительные линейные ускорения и сильные наклоны требуют отдельной проверки.

## Контур карты и траектории

`solve` выдаёт `map/map.yaml` и `map/map.pgm`, `inspection/trajectory.csv`, а при включённой кинематике ещё `inspection/continuous.csv`. В последнем файле `matched` обозначает датированный результат привязки лидарного скана. `prediction_only` обозначает прогноз по штатной одометрии, `anchor_age_s` показывает время с последней привязки. Прогноз не пересекает разрыв самой кинематики. Для трассировки исходные результаты на временах лидара сохраняются отдельно.

```sh
python -m mgts_nav.loop data/mapping out/official-01/map/trajectory.csv --config configs/official.json
python -m mgts_nav map data/mapping --close-loop --config configs/official.json --out out/closed
```

Первый вызов проверяет возвращение в стартовую зону по удалению конечных поз, выезду из стартовой зоны и двустороннему перекрытию сканов. Второй, если проверка прошла, добавляет измеренное относительное положение концов к графу поз, оптимизирует его и повторно собирает карту. В обычном синтетическом офисе ATE обхода составила 0,00768 м до и 0,00775 м после оптимизации. По умолчанию включён исходный вариант. Эксперимент проверяет петлю между концами записи, промежуточные петли требуют отдельного детектора.

## Для защиты

```sh
rviz2 -d configs/inspection.rviz
ros2 bag play out/official-01/rviz
```

Команды запускаются в двух терминалах с ROS 2. `/map` появляется в начале, `/pose` обновляется по исходным временам и `/path` содержит полный маршрут в конце. Готовые графические результаты можно открыть также в `map/route.png` и `inspection/route.png`. Проверено чтение записанных ROS-сообщений; интерактивный просмотр RViz и сборка Docker остаются проверками на машине с соответствующей средой.

## Воспроизвести испытания

```sh
python -m mgts_nav.stress out/rehearsal-01/data --map out/rehearsal-01/map/map.yaml
python -m mgts_nav.map_eval out/rehearsal-01/map/map.yaml
python -m mgts_nav.demo out/corridor-41 --layout corridor --seed 41
python -m mgts_nav.solve out/corridor-41/mapping out/corridor-41/inspection --config configs/example.json --out out/corridor-41-result
python -m mgts_nav.metrics out/corridor-41-result/inspection/trajectory.csv out/corridor-41/inspection_truth.csv
```

`map_eval` использует эталонную геометрию стандартного испытательного офиса. Вторая сцена — длинный коридор с нишами, другим маршрутом, увеличенной потерей лучей и изменившимся положением двери. В этом сценарии с seed 41, автоматическим стартом и всеми тремя потоками ATE инспекции составила 0,0156 м на 100 метках.
