# Совмещение карты и плана офиса

По одинаково названным углам стен и другим ориентирам инструмент переносит маршрут из системы карты на изображение плана. Входной CSV может содержать результат обхода или инспекции. Для оценки преобразования используются только ориентиры. На [примере наложения](plan-route.png) зелёная точка отмечает начало инспекции, красная — её конец.

## Входы и координаты

В [примере JSON](plan-landmarks.json) поле `map_m` содержит координаты ориентиров в метрах системы карты: та же система, что у столбцов `x,y` в `trajectory.csv`. В `plan_px` тем же именам соответствуют центры пикселей исходного изображения. Начало изображения в левом верхнем пикселе, U растёт вправо, V вниз. Например, на плане высотой 680 пикселей точка с V = 679 лежит на нижней строке.

Поле `metres_per_pixel` задаёт размер пикселя по обеим осям. При расчёте плоская система плана начинается в центре левого нижнего пикселя, X направлена вправо, Y вверх. Координаты плана равны `(U, H−1−V) × metres_per_pixel`. Искомое преобразование из карты в эту систему имеет вид `p = scale × R(angle) × map_xy + translation_m`. Положительный угол отсчитывается против часовой стрелки. По умолчанию масштаб равен 1. Флаг `--fit-scale` разрешает оценить единый положительный множитель.

Список `check` содержит имена отложенных точек. Остальные ориентиры используются для подгонки методом наименьших квадратов. Нужны как минимум две различимые точки для подгонки. Для контроля ошибок соответствий отметьте дополнительные, разнесённые по плану точки. Если забыто или изменено имя в одной из таблиц, команда сообщит имена расхождений. Обмен координатами под двумя существующими именами портит подгонку по всем точкам, поэтому команда дополнительно перебирает пары опор. Каждая пара задаёт преобразование, и для него считается, сколько опор оно объясняет точнее порога `--outlier-m`, по умолчанию 0,25 м. Если согласна большая часть опор, но не меньше трёх, остальные опоры перечисляются в `suspects` с предупреждением, а в подгонке остаются. При двух согласных опорах из четырёх выводится предупреждение `No majority`: виновника по таким данным определить нельзя. Отложенные точки с невязкой больше порога перечисляются в `check_outliers`. Единого порога для разных планов нет, поэтому его можно задать под точность разметки. Повтор имени внутри `map_m` или `plan_px` вызывает отказ: иначе JSON молча оставил бы только последнюю точку.

## Запуск из корня MGTS в Windows PowerShell

```powershell
$python = '..\Transport_MSK\.venv\Scripts\python.exe'
& $python -m mgts_nav.plan_alignment docs/office-plan.png docs/plan-landmarks.json out/inspection-result/trajectory.csv --fit-scale --out out/plan-registration
```

Укажите новый выходной каталог. В `route.png` записывается линия по точкам входного CSV в порядке времени. Линия между отсчётами служит для наглядности и может пересекать интервалы потери локализации. В `alignment.json` сохраняются угол, перенос, масштаб, невязка каждого ориентира в метрах плана и отдельные RMSE по обучающим и контрольным точкам.

## Проверка на синтетическом плане

[План](office-plan.png) получен из стен синтетического офиса при повороте 18°, масштабе 1,15 и переносе (7,6; 4,1) м. Координаты изображения округлены до пикселя, разрешение 0,02 м. По четырём опорам восстановлены угол 18,0211°, масштаб 1,150134 и перенос (7,60276; 4,10024) м. RMSE составила 2,13 мм на опорах и 4,87 мм на двух отложенных ориентирах. Это ошибка совмещения искусственного плана. Точность траектории робота измеряется отдельно.

Тест `python -m pytest -q tests/test_plan_alignment.py` также проверяет фиксированный масштаб, независимость подгонки от отложенных точек, совпадающие опоры, опечатку в имени и перестановку координат двух ориентиров.
